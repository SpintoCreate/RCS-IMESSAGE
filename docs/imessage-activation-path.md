# Public rustpush activation path: source audit

Checked 2026-10-22. This is a source and documentation review, not a registration test. No Apple request, relay pairing, credential extraction, or device identity change was performed. Direct iMessage remains disabled in UnifiedMessages.

## Conclusion

I found **no upstream-documented, working authorization path for a third-party Android client using only the public rustpush source**. OpenBubbles [documents setup for its own app](https://openbubbles.app/quickstart.html) using a genuine Mac code or a supported iPhone relay; its [phone-number guide](https://openbubbles.app/docs/pnr.html) names ValidationRelay/TrollStore and says the iPhone must stay online. These are user setup instructions for OpenBubbles, not a published third-party activation API, Apple approval, or a grant to redistribute private signing material. Its [FAQ](https://openbubbles.app/docs/faq.html) describes Apple's validation of hardware information and the possibility of account/device restrictions.

This is a statement about the inspected public sources, not proof that no private arrangement or future method can exist. The app pins [rustpush `a7fab473`](https://github.com/OpenBubbles/rustpush/tree/a7fab473e7a33325a760635285db2860de8e1cb0); the public repository HEAD checked here was [`b3c96c2`](https://github.com/OpenBubbles/rustpush/tree/b3c96c23e1aae78d1229ebaccb12027624f1eaff). Both still embed the same FairPlay file paths. Neither README documents a third-party production signing path.

## What can be established about the shipped OpenBubbles release

The app's [Rust manifest](https://github.com/OpenBubbles/openbubbles-app/blob/eed1b6332efbb17adbf5ebfa2263ad770169f75e/rust/Cargo.toml#L1-L13) links the pinned rustpush source, and its [public Android CI workflow](https://github.com/OpenBubbles/openbubbles-app/blob/eed1b6332efbb17adbf5ebfa2263ad770169f75e/.github/workflows/build.yml#L45-L74) copies the public legacy pair into all ten required paths, then **attempts** a debug alpha APK build. The workflow itself even notes an expected build failure from another dependency. It does not establish the provenance or effectiveness of signing material in a separately distributed Android release. The inspected [GitHub Releases listing](https://github.com/OpenBubbles/openbubbles-app/releases) offered Linux archives, not a release Android APK with matching build provenance. I did not inspect a shipped APK for embedded keys.

For a release built from this source, the activation signer would select a pair compiled into its native library, sign the activation info locally, and send it directly to Apple. The iPhone relay does **not** deliver a FairPlay key at runtime. Public evidence does not establish whether a currently working release used the public legacy pair, a separately supplied pair, or a different build path. Do not present any of those possibilities as a confirmed fact, and do not infer reusable rights from a working binary.

## Build inputs versus live activation

| Stage | What public source provides | What remains unproved or missing |
| --- | --- | --- |
| Compile rustpush | The [activation source](https://github.com/OpenBubbles/rustpush/blob/a7fab473e7a33325a760635285db2860de8e1cb0/src/activation.rs#L38-L65) uses `include_bytes!` for **ten `.crt`/`.pem` pairs** under `certs/fairplay/`. The public Git tree contains **zero** files under that path; it contains one `certs/legacy-fairplay` pair. The [upstream CI](https://github.com/OpenBubbles/rustpush/blob/a7fab473e7a33325a760635285db2860de8e1cb0/.github/workflows/build.yml#L27-L47) explicitly calls its copying step “Set up fake Fairplay keys” and copies that legacy pair into all ten paths. OpenBubbles' [app CI](https://github.com/OpenBubbles/openbubbles-app/blob/eed1b6332efbb17adbf5ebfa2263ad770169f75e/.github/workflows/build.yml#L45-L65) does the same. | Without bytes at the ten paths, compilation fails. Copies from the public legacy pair satisfy file inclusion, but a successful compile is **not evidence** that Apple will accept the resulting signature. Whether the legacy pair works for a particular activation was not tested here. |
| Build Android binding | The pinned source, public `apple-private-apis` submodule, Rust Android target, NDK, `protoc`, and the compatible `remote-anisette-v3` feature can build the isolated JNI experiment. | This only proves native linking. The default Mac validation feature references `OpenAbsinthe-Stub`; the stub is not a proven production Mac validation service. The build uses upstream's compile-only FairPlay placeholders and exposes no activation route. |
| Obtain relay inputs | [rustpush `RelayConfig`](https://github.com/OpenBubbles/rustpush/blob/a7fab473e7a33325a760635285db2860de8e1cb0/src/relay.rs#L43-L68) requests `get-version-info`, then [requests `get-validation-data`](https://github.com/OpenBubbles/rustpush/blob/a7fab473e7a33325a760635285db2860de8e1cb0/src/relay.rs#L147-L168) using a pairing code. The published [iPhone relay](https://github.com/OpenBubbles/relayserver/blob/630721fef21e3d072e72d92df957a66c0b2b0851/src/relay.rs#L120-L135) implements exactly those two commands. | A live compatible iPhone, supported iOS/TrollStore setup, pairing service, and successful validation response are required. None was tested here. A returned blob is not Apple activation or IDS registration. |
| Get an Apple push certificate | rustpush constructs a CSR, [signs its activation info with its embedded FairPlay pair, and posts to Apple](https://github.com/OpenBubbles/rustpush/blob/a7fab473e7a33325a760635285db2860de8e1cb0/src/activation.rs#L103-L135). It requires a `DeviceCertificate` in Apple's response. [APS connection](https://github.com/OpenBubbles/rustpush/blob/a7fab473e7a33325a760635285db2860de8e1cb0/src/aps.rs#L1274-L1292) triggers this when no keypair exists. | No public document supplies an authorized, independently verified production FairPlay signer for this third-party app. No Apple response was observed. Compilation, relay pairing, and validation-data generation cannot stand in for a returned certificate. |
| Register and message | [IDS registration](https://github.com/OpenBubbles/rustpush/blob/a7fab473e7a33325a760635285db2860de8e1cb0/src/ids/user.rs#L1090-L1120) uses validation data and an APS keypair. OpenBubbles [documents renewal](https://openbubbles.app/docs/renewal.html), including continuous iPhone relay availability. | A usable APS connection, Apple account/phone handle registration, one sent and one received iMessage, and later renewal remain untested. The relay seeing a validation request does not prove any of them. |

The `.pem` filename is not evidence of format or authority; rustpush's signer parses those bytes as a private key. This audit did not inspect key bytes. The earlier diagnostic build copied the public legacy pair into ignored build output strictly to compile; it must not be treated as a production signing source.

## What the iPhone relay can do

The published protocol can supply **real device version/identifier fields and fresh validation data** from an iPhone the user controls. The current [StablePush candidate](https://github.com/SpintoCreate/StablePush/blob/d1237b401fef50b38236366b3025c1606400777a/README.md) implements those same two commands and explicitly reports no physical registration test. It is not an Android rustpush replacement.

The published relay **does not** expose FairPlay signing, return Apple's activation certificate, log in to an Apple account, or prove message delivery. Those steps occur in the Android/rustpush process and at Apple's services. Adding a new signing endpoint would be a new, unreviewed protocol and would not itself establish authorization. The original `relayserver` also [disables TLS certificate verification for its validation HTTP client](https://github.com/OpenBubbles/relayserver/blob/630721fef21e3d072e72d92df957a66c0b2b0851/src/nac.rs#L29-L38); that implementation cannot be adopted unchanged under this project's TLS requirement.

The pinned [relay activation fields](https://github.com/OpenBubbles/rustpush/blob/a7fab473e7a33325a760635285db2860de8e1cb0/src/relay.rs#L72-L84) set `MacOS`/`iMac13,1` labels while taking serial and unique device ID from the relay. This is what the source does; it is not evidence that changing labels, substituting identifiers, or rotating a device identity would fix an Apple rejection. None was changed here.

An upstream clarification would need to answer: whether third-party clients are supported; whether the publicly copied legacy pair is intended and authorized for live activation; whether a rights-cleared signing service or API exists that does not disclose private keys; and what evidence constitutes successful APS/IDS registration. Ask the rustpush/OpenBubbles maintainers for documentation and the relevant rights holders for permission, rather than requesting private keys or extracting them from a device. Even their technical approval would not itself be Apple authorization.

**Decision gate:** Keep the provider disabled. The next claim of working support requires a rights-cleared runtime signing path, a redacted successful `DeviceCertificate`/APS/IDS sequence on the user's own devices, and an actual send-and-receive test. On Apple rejection, stop repeated attempts without rotating identity. Do not collect or share pairing codes, credentials, device identifiers, validation blobs, or messages.
